# Decisiones técnicas

Contexto que condicionó varias decisiones: el entorno donde se construyó el proyecto **no tenía acceso a internet para instalar paquetes** (npm/pip bloqueados). Solo se podían usar herramientas preinstaladas: Node.js 22.23, TypeScript 6, esbuild 0.28, React 19.2, Playwright 1.63 con Chromium y PostgreSQL 16 (servidor, sin controlador para Node). Las decisiones priorizan lo verificable aquí sin simular nada.

| ID | Decisión | Alternativas evaluadas | Justificación |
|---|---|---|---|
| DT-01 | **React 19 + TypeScript** para la interfaz, empaquetado con **esbuild** | Next.js, Vue, Vite | React y esbuild estaban disponibles; una SPA basta (no hay SEO ni SSR). esbuild produce un bundle de 285 KB en < 1 s. |
| DT-02 | **Servidor HTTP propio sobre `node:http`** (router, middleware de seguridad, errores) | Express, NestJS, Fastify | No instalables. El servidor resultante no tiene dependencias de terceros en ejecución, lo que reduce la superficie de ataque. Capas separadas: rutas → servicios → repositorios. |
| DT-03 | ~~SQLite como único motor~~ → PostgreSQL en servidor (DT-20) y SQLite en local (DT-26) | PostgreSQL + Prisma/Drizzle | Sin controlador PostgreSQL ni ORM instalables. SQLite es persistencia real, transaccional, con claves foráneas y `CHECK`; adecuada para un equipo (decenas de usuarios, una instancia). El acceso está aislado en repositorios con SQL parametrizado → migrar a PostgreSQL implica reescribir `src/server/db` y `src/server/repositories` sin tocar servicios ni interfaz. Ver KNOWN_ISSUES. |
| DT-04 | **Validación compartida** cliente/servidor (`src/shared/validation.ts`) | Zod | Zod no instalable. Se implementó un validador tipado pequeño con los mismos esquemas en ambos lados (rechaza campos desconocidos, limpia caracteres de control). |
| DT-05 | **Sesiones en base de datos + cookie HttpOnly** y **token CSRF** por sesión en cabecera `X-CSRF-Token` + verificación de `Origin` | JWT | Las sesiones de servidor se pueden revocar (desactivar usuario, cambiar contraseña). El token de sesión se guarda como hash SHA-256. |
| DT-06 | **scrypt** (N=16384, r=8, p=1, sal de 16 bytes) para contraseñas | bcrypt, argon2 | Nativo en `node:crypto`; comparación en tiempo constante; hash ficticio para igualar tiempos cuando el correo no existe. |
| DT-07 | **Declaraciones de tipos mínimas para React** (`src/client/types/react-shim.d.ts`) | `@types/react` | `@types/react` no estaba disponible. El *shim* cubre solo la API usada y permite `typecheck` estricto. Al disponer de red se puede instalar `@types/react` y eliminar el archivo (ver KNOWN_ISSUES). |
| DT-08 | **Lint con la API del compilador TypeScript** (`scripts/lint.mjs`, 12 reglas) | ESLint | ESLint no instalable. Reglas enfocadas en riesgos reales: `any`, `console`, `alert`, `eval`, `innerHTML/dangerouslySetInnerHTML`, `localStorage`, SQL concatenado, `catch` vacío, `.only/.skip`, archivos > 600 líneas. |
| DT-09 | **`node:test`** para unitarias e integración, cobertura V8 con umbrales | Vitest, Jest | Nativo; ejecuta TypeScript directamente (Node ≥ 22.18 elimina tipos). Umbrales: global 80 % líneas/funciones, 70 % ramas; lógica de negocio 90 % líneas. |
| DT-10 | **Playwright** con Chromium real para E2E y visuales, con dos servidores aislados | Cypress | Requerido; disponible. Las visuales comparan contra capturas de referencia y además verifican desbordes y superposiciones. |
| DT-11 | **Semanas ISO-8601** con identificador `AAAA-Wnn` y fecha «hoy» según `APP_TIMEZONE` (America/Bogota) | Numeración relativa del prototipo | Evita ambigüedad entre años; `APP_TODAY` fija la fecha solo en desarrollo/pruebas (ignorado en producción). |
| DT-12 | **Minutos enteros para estimados, segundos enteros para tiempo real**; el tiempo real es la suma de un libro de registros (`time_entries`) | Horas decimales (prototipo) | Sin errores de redondeo; cada cambio queda trazable (`timer`, `quick`, `adjust`, `seed`). Corregir el real crea un ajuste por la diferencia. |
| DT-13 | **Borrado lógico** de tareas (`deleted_at`) | Borrado físico | Permite «Deshacer» y auditoría sin perder referencias de retraso. |
| DT-14 | **Reglas de negocio en `src/shared/rules.ts`**, usadas por servidor (fuente de verdad) y cliente (actualización optimista) | Solo servidor | La interfaz responde al instante y el servidor garantiza la consistencia; además la tabla tiene `CHECK ((status='done') = (progress=100))`. |
| DT-15 | **Un cronómetro por usuario en el servidor** con tope `TIMER_MAX_HOURS` | Por navegador (prototipo) | Sobrevive a recargas y cambios de equipo; evita registrar días por un cronómetro olvidado. |
| DT-16 | **Roles `admin` (Coordinación) y `member` (Colaborador)** | Más roles | Cubren las responsabilidades que sugiere el prototipo (planear la semana vs. ejecutar y registrar). |
| DT-17 | **Docker multi-etapa + Caddy** (HTTPS automático) y alternativa systemd | Nginx + certbot | Caddy simplifica TLS; la imagen final no lleva `node_modules`. No se pudo ejecutar Docker en el entorno (sin daemon). |
| DT-18 | **CSP estricta** sin `unsafe-inline` en scripts ni estilos | — | React aplica estilos en línea mediante CSSOM, permitido por CSP. Verificado: cero violaciones en la consola durante E2E. |
| DT-19 | Datos semilla **desplazados a la semana actual** | Fechas fijas de 2026 | Al instalar, la demo luce como el prototipo en la semana en curso. |
| DT-20 | **PostgreSQL 16** (v1.1.0), a pedido del cliente que ya opera un servidor 16.13 | Mantener SQLite | Permite varias instancias, respaldos y administración con las herramientas del servidor existente. Tipos nativos (`uuid`, `timestamptz`, `date`, `boolean`, `jsonb`), restricciones CHECK/FK/UNIQUE con nombre, índice parcial para tareas activas |
| DT-21 | **Cliente PostgreSQL propio** (`src/server/db/pg/`): protocolo v3, SCRAM-SHA-256/MD5, TLS hasta `verify-full`, pool | Librería `pg` | `pg` no era instalable sin red. El cliente se validó contra PostgreSQL 16 real (vector RFC 7677 para SCRAM, 4 modos SSL, cortes de conexión, timeouts). Sustituible por `pg` cambiando solo `db/database.ts` |
| DT-22 | **Parámetros con nombre** (`$nombre`) traducidos a posicionales, y **transacciones con `AsyncLocalStorage`** | Pasar la conexión a cada repositorio | Los repositorios no cambian de firma dentro o fuera de una transacción; los savepoints dan anidamiento |
| DT-23 | **Dos roles** (`planeacion_owner` para DDL, `planeacion_app` solo DML) y esquema propio; `DB_AUTO_MIGRATE=false` en producción | Un rol dueño de todo | Mínimo privilegio: una vulnerabilidad en la aplicación no puede alterar ni borrar el esquema |
| DT-24 | **Bloqueos consultivos** para migraciones y creación de semanas, más traducción de errores SQLSTATE a HTTP | Confiar solo en la aplicación | Con varias instancias, las reglas de unicidad se garantizan en la base y los conflictos llegan al usuario como 409/422 claros |
| DT-25 | **Identificadores `uuid`** validados antes de consultar | `text` | Integridad de tipo; evita errores 22P02 por identificadores mal formados (responden 404/422) |
| DT-26 | **Dos motores (v1.2.0): SQLite en local y PostgreSQL en servidor**, detrás de una interfaz `Database` común | Solo PostgreSQL en todos los entornos | Pedido del cliente: desarrollo sin instalar un servidor de base de datos. SQL común en repositorios; migración propia por motor con las mismas reglas; errores de SQLite traducidos a SQLSTATE; la batería completa se ejecuta en ambos para evitar divergencias |
